# ADR-0021: Dual-Time Control Plane with Merkle/HSM Anchoring

**Status:** Accepted  
**Date:** 2026-03-03  
**Supersedes:** None  
**Superseded by:** None  

## Context

Industrial control systems require both real-time operational control and immutable audit trails for regulatory compliance and forensic analysis. Traditional SCADA systems struggle with this dual requirement, often sacrificing audit capabilities for real-time performance or vice versa.

0xSCADA addresses this challenge with a **Dual-Time Control Plane** architecture that separates operational concerns from integrity verification while maintaining cryptographic proofs of all system events.

## Decision

We implement a Dual-Time Control Plane consisting of:

1. **Real-Time Operational Plane** - Immediate control and monitoring
2. **Integrity Verification Plane** - Cryptographic audit trail with Merkle tree anchoring and HSM signing

## Components

### 1. Event Integrity Pipeline Core

**File:** `server/integrity/pipeline.ts`  
**Issues:** #287

**Purpose:** Ingests all system events, computes SHA-256 hashes, and batches them into configurable time windows.

**Key Features:**
- Configurable time windows (default: 1 minute)
- Maximum batch sizes (default: 1000 events)
- Forced flush intervals (default: 30 seconds)
- Canonical event representation for consistent hashing
- Event emission for real-time monitoring

**Data Flow:**
1. SCADA events enter the pipeline
2. Events are canonicalized and SHA-256 hashed
3. Events are batched by time windows
4. Batches are emitted for Merkle tree construction

### 2. Merkle Tree Construction

**File:** `server/integrity/merkle.ts`  
**Issues:** #288, #290

**Purpose:** Builds Merkle trees from event batches, generates inclusion proofs, and verifies proof validity.

**Key Features:**
- Clean SHA-256 Merkle tree implementation (no external dependencies)
- Inclusion proof generation and verification
- Batch proof operations
- Tree storage and management
- Deterministic tree construction

**Data Flow:**
1. Receives event batches from pipeline
2. Constructs Merkle trees from event hashes
3. Generates Merkle root for HSM signing
4. Provides inclusion proofs for individual events

### 3. HSM/PKCS#11 Signing

**File:** `server/integrity/hsm.ts`  
**Issues:** #291, #292

**Purpose:** Cryptographically signs Merkle roots using Hardware Security Modules or software keys.

**Key Features:**
- Abstract signer interface for multiple backends
- Software signer for development (uses Node.js crypto)
- PKCS#11 interface ready for HSM integration
- Key management and storage
- Signature verification

**Signing Modes:**
- **Software Mode:** Local RSA keys for development
- **PKCS#11 Mode:** Hardware Security Module integration
- **Hardware Mode:** Future extension point for other HSM interfaces

## Time Separation Strategy

### Real-Time Plane (Microsecond Precision)
- Immediate device control and monitoring
- Sub-second response requirements
- Operational safety and control loops
- Direct PLC/RTU communication

### Integrity Plane (Second/Minute Precision)
- Event batching and cryptographic processing
- Merkle tree construction and signing
- Immutable audit trail creation
- Regulatory compliance and forensics

### Synchronization Points
1. **Event Ingestion:** Real-time events are immediately captured
2. **Time Windows:** Events are batched by configurable time periods
3. **Cryptographic Anchoring:** Periodic HSM signing of Merkle roots
4. **Audit Trail:** Immutable record with cryptographic proofs

## Security Properties

### Integrity Guarantees
- **Event Integrity:** SHA-256 hashing prevents event tampering
- **Batch Integrity:** Merkle trees provide cryptographic batch verification
- **Root Integrity:** HSM signing prevents root forgery
- **Temporal Integrity:** Time windows provide chronological ordering

### Audit Properties
- **Non-repudiation:** HSM signatures provide proof of authenticity
- **Immutability:** Merkle tree structure prevents historical modification
- **Completeness:** All events are captured and hashed
- **Verifiability:** Independent parties can verify event inclusion

### Attack Resistance
- **Event Injection:** Requires access to HSM signing keys
- **Event Deletion:** Leaves cryptographic gaps in Merkle trees
- **Event Modification:** Changes event hashes, breaking Merkle proofs
- **Replay Attacks:** Time windows and sequence numbers prevent replays

## Performance Characteristics

### Real-Time Plane
- **Latency:** < 1ms for control operations
- **Throughput:** 10,000+ operations/second
- **Availability:** 99.99% uptime requirement

### Integrity Plane
- **Latency:** 1-60 seconds for audit trail updates
- **Throughput:** 1,000+ events/second sustained
- **Storage:** Logarithmic growth with Merkle tree compression

## Alternatives Considered

### Single-Time Architecture
**Rejected:** Cannot meet both real-time and audit requirements simultaneously.

### External Audit System
**Rejected:** Creates trust boundary and potential data loss during transfers.

### Blockchain Integration
**Deferred:** Adds complexity and latency. May be reconsidered for inter-organization verification.

### Database Triggers
**Rejected:** Cannot provide cryptographic integrity guarantees.

## Consequences

### Benefits
- **Dual Requirements:** Satisfies both real-time and audit needs
- **Cryptographic Security:** Strong integrity and non-repudiation guarantees
- **Scalability:** Merkle trees provide logarithmic verification complexity
- **Flexibility:** Multiple HSM backends and configuration options
- **Compliance:** Meets regulatory requirements for immutable audit trails

### Risks
- **Complexity:** Multiple subsystems increase operational complexity
- **Storage Growth:** Audit trails grow over time (mitigated by Merkle compression)
- **HSM Dependency:** Critical path through hardware security modules
- **Clock Synchronization:** Requires accurate time sources for time windows

### Migration Path
- Phase 1: Deploy foundational components
- Phase 2: Integrate with existing SCADA systems
- Phase 3: Enable full audit trail verification
- Phase 4: Migrate to hardware HSMs in production

runtime.** The only anchor path instantiated at server bootstrap

`ANCHOR_BACKEND=l2|both` to activate at all; the canonical path is
0xSCADA-node via NATS. `server/integrity/relayer.ts` and `verifier.ts`
have zero importers and zero tests.
